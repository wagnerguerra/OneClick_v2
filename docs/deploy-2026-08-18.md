## 1. O que o Service Manager faz sozinho

Publicar pelo SM já cobre **todo o código** e **todo o schema**. Os três SQLs novos estão em
`packages/db/prisma/sql/`, que é a pasta que o deploy aplica no **stage 4.5**, em ordem
alfabética, com `ON_ERROR_STOP=1`. Todos são aditivos e idempotentes — rodam a cada deploy sem
duplicar nada.

| Arquivo | O que cria |
|---|---|
| `add_compra_mensagem_thread.sql` | `compra_mensagens.parent_id` + índice + FK (responder mensagem no pedido) |
| `add_documentos_internos.sql` | 6 tabelas do módulo Documentos Internos |
| `add_reunioes.sql` | 6 tabelas do módulo Reuniões |

> ⚠️ **Atenção para as próximas vezes.** Existem duas pastas de SQL no repositório e **só uma é
> aplicada**: `packages/db/prisma/sql/`. A `packages/db/migrations/` não é lida por nada — SQL
> colocado lá simplesmente não roda em produção, e o módulo sobe com "relation does not exist".
> Estes três nasceram na pasta errada e foram movidos antes de publicar.

## 3. O que NÃO entra pelo SM — a carga dos documentos

O Service Manager aplica schema, não dados nem arquivos. Depois do deploy, para os 67 documentos
e as 265 revisões aparecerem, faltam **dois passos**, nesta ordem:

### 3.1. Os arquivos (52 MB, 265 arquivos)

Precisam chegar em `uploads/documentos-legado/` **dentro do container da API**. Da máquina que
enxerga o `\\192.168.0.7\wwwroot`:

```bash
# 1) gera a pasta local (já feita — apps/api/uploads/documentos-legado)
node scripts/legacy-v1-documentos-import.js

# 2) sobe para a VPS e joga no volume do container
scp -i ~/.ssh/oneclick_deploy -r apps/api/uploads/documentos-legado root@72.60.155.69:/tmp/
ssh -i ~/.ssh/oneclick_deploy root@72.60.155.69 \
  'docker cp /tmp/documentos-legado oneclick-api:/app/uploads/ && rm -rf /tmp/documentos-legado'
```

> O caminho dentro do container precisa bater com o `UPLOADS_DIR` da API (`<cwd>/uploads`).
> Confira com `docker exec oneclick-api ls uploads/documentos-legado | wc -l` — esperado **265**.

### 3.2. Os dados

O script gera `scripts/out/v1-documentos-internos.sql` (idempotente, casa por `legacy_id`).
Aplicar **depois** do `add_documentos_internos.sql` ter rodado no deploy:

```bash
scp -i ~/.ssh/oneclick_deploy scripts/out/v1-documentos-internos.sql root@72.60.155.69:/tmp/
ssh -i ~/.ssh/oneclick_deploy root@72.60.155.69 \
  'docker exec -i n8n-postgres-1 psql -U oneclick -d oneclick -v ON_ERROR_STOP=1 < /tmp/v1-documentos-internos.sql'
```

Esperado ao final: 4 tipos, 13 processos, 67 documentos, 265 revisões, 114 elaboradores.

> **Regere o SQL antes de aplicar** (`node scripts/legacy-v1-documentos-import.js`). Ele resolve
> os ids de usuário consultando o banco local, e o dev é um snapshot: um arquivo gerado há dias
> pode carregar id de usuário que não existe em produção. Como esses ids são **soltos (sem FK)**,
> um id inválido não dá erro — grava um ponteiro para o nada. Foi o que aconteceu na primeira
> geração, quando o casamento por nome pegou o "Wagner Guerra" da **L&L** em vez do da Central.
> O script passou a filtrar os usuários pela empresa de destino.

> **Por que não entra na pasta do deploy:** são mais de mil comandos que rodariam a cada
> publicação, e sem os arquivos do passo 3.1 o módulo mostraria documento sem anexo. É carga de
> uma vez só.

### 3.3. Se a carga falhar com `null value in column "atualizado_em"`

Acontece porque a tabela nasceu do `prisma db push` (stage 4 do deploy, que roda **antes** dos
SQLs): o `@updatedAt` do Prisma é aplicado pelo cliente, não pelo banco, então a coluna vem
NOT NULL e **sem default** — e o `CREATE TABLE IF NOT EXISTS` do SQL vira no-op, sem chance de
aplicar o default. Qualquer INSERT cru quebra.

Os `add_documentos_internos.sql` e `add_reunioes.sql` já trazem o conserto (um
`ALTER COLUMN ... SET DEFAULT CURRENT_TIMESTAMP` no fim). Se cair nisso, reaplique o SQL do
módulo e repita a carga.

## 4. Depois de conferir

Com os documentos no ar e conferidos, o módulo `sgq_documentos` do v1 pode ser desativado pelo
procedimento de sempre: aviso na tela, botão desabilitado e bloqueio server-side. Não desativar
antes de validar a carga — o v1 continua sendo a fonte enquanto isso.
